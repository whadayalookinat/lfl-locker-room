# v0.6 login hardening and deployment gate

Status: design/QA plan only. Migration 005 has been applied by commissioner. No Edge Functions deployed.

## Current risk
The username-login function checks login_limit_status, then makes a network request to Supabase Auth, then records failure. Parallel requests can all pass the status check before any failure is recorded. Do not claim the current code enforces a strict ten-attempt cap under concurrency.

Unknown usernames return early, so a high-volume client can still call the function without touching the per-account counter. A valid Origin header is not sufficient to authenticate clients.

## Recommended implementation
1. Add a server-side atomic attempt reservation RPC, guarded by a per-account row lock, to limit concurrent and sequential attempts. Track in-flight reservations and release them on completion or expiry. Avoid holding a database transaction open across an external Auth request. Treat expired reservations conservatively. Carefully define whether the ten-attempt rule counts failures or started attempts.
2. Add an independent short-window request throttle at the edge for both known and unknown usernames. Use only verified platform-provided client IP metadata (not an arbitrary client-supplied forwarded header), or use a managed edge gateway. Rate limits should not disclose account existence.
3. Add abuse safeguards for commissioner accounts: no username-triggered hard lockout, but still enforce request/IP throttling and Supabase Auth protections.
4. Do not persist raw passwords, raw tokens, or plaintext IP addresses in logs or tables.
5. Make login error messages consistent and return 429 for temporary throttling.
6. Run negative tests before exposing the endpoint publicly.

## Test matrix
- Valid username + correct password -> session; counter resets.
- Wrong password attempts 1 through 9 -> rejection and counter increments.
- Wrong password attempt 10 -> lock for 30 minutes; subsequent attempt -> 429.
- Unlock by active commissioner -> immediately clears counter.
- Unlock by participant or anonymous request -> 403 or 401.
- Expired lock -> next attempt permitted.
- Unknown usernames -> throttled under sustained abuse, without account enumeration.
- Parallel requests >10 -> bounded authentication attempts, not just eventual counter increment.
- Disabled member -> no login.
- Renamed username -> new username works, old username fails, UUID/comments unchanged.
- Password reset -> new password works; verify existing sessions separately.
- Commissioner -> cannot be locked out by deliberate username failures; high-volume attempts still throttled.
